# Dorey v0.2.2

状态：发布候选。待接受修订的刷新阻塞已修复并完成本地回归；正式发布仍需确认目标提交 CI 通过，尚未创建 tag 或 GitHub Release。

## 变更

- 评论支持“修订”和“解释”，默认选择修订；编辑评论时可以切换类型。
- 根据待提交内容显示“提交修订”“提交问题”或“提交全部”，并分别统计两类评论。
- 解释型评论由原 Agent 会话回答，Dorey 仅展示轻量回执，不重复显示解释正文。
- 纯解释请求保留原 Markdown，即使 Agent 意外返回改写内容，也不会产生可接受的文档修订。
- 混合提交先在原会话回答问题，再处理修订意见；有文档变化时才显示修订、差异和接受操作。
- Codex / TraeX 的请求提示及 foreground poll 输出同步携带评论类型和处理约束。
- 修复待接受修订在刷新后丢失的问题：有改动的结果在接受写回成功后才确认，刷新可恢复修订、差异和待处理评论；纯解释及无改动结果继续立即确认。
- 接受写回冲突保留待接受结果；写回成功后确认请求失败可重试。接受较新的方案会同时结束同文档、同目标的较早 completed 方案，避免旧方案再次出现。

## 兼容与边界

旧评论未携带 `kind` 时按 `revision` 处理；新解释评论使用 `kind: "explanation"`。非空“全文修订要求”也代表修订意图，因此与解释评论同时提交时允许产生文档修订。

原会话仍需保持 foreground poll；页面的“已回答”回执来自 Agent 返回结果，并不验证原对话中是否实际发出了答案。解释正文应由处理请求的 Agent 在原对话中提供。

接受修订仍执行原文件 hash 校验和原子写回；外部变更冲突时不覆盖原文件。队列仍持久化 completed 结果；有改动时 acknowledge 延后到接受写回成功，纯解释及无改动仍在结果展示后确认。结束评审协议保持不变。

## 发布约定

沿用 GitHub `vX.Y.Z` tag 和 `Dorey vX.Y.Z` Release 命名。项目保持 `private: true`，不发布到 npm registry。v0.2.0 提供 npm tarball 附件，v0.2.1 是无附件的源码 Release；v0.2.2 恢复准备与版本一致的安装包。

修复由 [PR #9](https://github.com/hopeloop/dorey/pull/9) 单独承载，base 为 `codex/comment-types`。[发布准备 PR #8](https://github.com/hopeloop/dorey/pull/8) 接在修复分支之上，仅增加版本与发布文档。应先合入修复、再合入发布准备；最终功能分支仍需进入 `main`，合入功能分支不等于正式发布。

正式发布时：

1. 确认功能及发布准备改动已进入 `main`，目标提交的 GitHub Actions 全绿。
2. 从该提交的干净 checkout 执行 `npm ci`、下方全量门禁及打包检查。
3. 使用 `npm pack --pack-destination /tmp` 生成 `dorey-0.2.2.tgz`；隔离安装验证 `dorey --help`，检查包内版本、CLI 与 Web 产物，并计算 SHA-256。
4. 在已验证的提交上创建并推送 `v0.2.2`，使用 `gh release create v0.2.2 /tmp/dorey-0.2.2.tgz --verify-tag --title 'Dorey v0.2.2' --notes-file <release-notes>` 发布。正式说明应包含变更、验证结果、安装方法和校验和，移除本文的候选状态及待执行步骤。
5. 回查 tag 目标和 Release 附件，再验证 README 中的下载地址可用。
